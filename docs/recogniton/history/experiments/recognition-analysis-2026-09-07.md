> 历史分析：结论限于原文注明的代码、数据及权重版本，本次未重做训练或性能测量。当前行为见[架构](../../recognition.md)和[运行说明](../../guides/running.md)。

## 1. 结论：有不利项，但不能把整套增强都判为变差

**最直接的变化是删除 `remove_red_seal()`：原先预处理承担的去章任务，现在交给 RGB 模型学习，而训练没有补上对应的章覆盖增强。红章回退有明确机制依据。**

如果只问“随机数据增强是否改得更不利”：新增反色、加强颜色变化值得怀疑；模糊、噪声和擦除其实减弱了。**尚未完成同条件训练对照，不能断言哪一项降低了多少准确率。**
上一版没有追到去红调用的删除，又把推理 batch 一致性当成主要排查方向，没回答这个问题。

### dataset.py 逐项比较

比较 `b02fd0e` 与 `288a522` 后的公共加载链路；09-03 的 PackedSequence 修改另行判断。

| 项目 | 调整前 | 当前 | 对红章的判断 |
| --- | --- | --- | --- |
| 去红 | RGB 阶段调用 `remove_red_seal`，随后转灰度 | 删除去红；新训练保留 RGB | **明确改变任务难度**：保留颜色信息，也把原章笔画重新交给模型处理；缺少对应训练时有回退风险 |
| ColorJitter | 每次执行；contrast=0.2、saturation=0.1；当时已经转灰度 | p=0.7；contrast=0.25、saturation=0.35、hue=0.03 | 现在真正改变章与正文的颜色线索；可能帮助适应扫描偏色，也可能增加学习难度，需单测，不能直接认定有害 |
| Invert | 无 | p=0.08 | **优先排查**：红章变青色、白底变黑底。白字 UI 的极性增强被同时施加给文档，任务与实际红章分布不完全对应 |
| Autocontrast | 无 | p=0.2 | 改变各通道对比度，不产生新的章遮挡；收益未知 |
| 模糊 | p=0.3，sigma 上限 1.0 | p=0.15，上限 0.8 | 退化减轻；但仍在最终 32 高图上执行，可能混合细笔画与章边 |
| 噪声 | p=0.3，std=0.02，不限制范围 | p=0.15，std=0.015，限制到 [0,1] | 退化减轻，不能列作“增强变得更激进”的证据 |
| 随机擦除 | p=0.18，面积 2%～10% | p=0.05，面积 0.5%～3% | 破坏概率和面积都减小；**两版都不是章叠加模拟** |
| 旋转/透视 | ±2°；透视 p=0.3 | 删除 | 降低紧框文字被切掉的风险，也减少几何变化覆盖；不能据此直接归因红章回退 |

当前增强只有全图颜色变化、模糊、噪声和随机块，没有“正文上叠加红色章文字、圆弧、星形”的监督任务。**RGB、ColorJitter、RandomErasing 都不能自动补上这项能力。**

## 2. 实际核对：去红删除有影响，恢复旧函数也会损失像素

对清单 43 张真实红章图，在内存中运行原版去红函数及默认 SciPy 形态学处理：

- **38 张发生像素改写，5 张被旧保护规则原样保留**，因此不能把全部错误都解释为去红删除。
- 38 张中合计 **2,227 个低色差深色像素被抹白**。定义为 `max(R,G,B)<150 且 max-min<20`；说明有正文笔画损失风险，不能换算成丢失字符数。
- 旧白字裁剪对这 43 张均未改变尺寸；新旧缩放宽度相差超过 1 px 的只有 1 张。

具体反例：`000570-000010.png` 虽然章盖住“审计范围”等正文，但旧函数内容留存比 0.474，小于 0.5，**旧版也不去红**。
`000874-000025.png` 新旧缩放均为 1090×32，旧函数改变 4,403 像素，适合隔离颜色处理。
`000249-000009.png` 则同时有去红和宽度 800→922 的变化，不能混为单一原因。

旧函数先检查内容保留比例，再膨胀、闭运算；后续扩张仍可能抹到相邻黑笔画。它也无法可靠区分印章和合法红字，**不建议直接恢复成全局预处理**。
以上是像素对照，不是 OCR 准确率对照。

随机擦除还有一个共存问题：`value="random"` 使用标准正态随机值，放在 Normalize 前会产生 `2Z-1` 的随机块。本次 10 张真实图各跑 100 个 seed，52/1,000 次越出正常 [-1,1] 图像范围，极值为 -8.638 和 7.074。
**旧版也存在这个问题，不能算成本次新增回退。** 它应独立消融，而不是用来替代红章模拟。[TorchVision 实现](https://docs.pytorch.org/vision/stable/_modules/torchvision/transforms/transforms.html#RandomErasing)

## 3. dataset.py 的明确方案

**保留共享 RGB 加载、完整框缩放及 batch 长度契约。重点调整文档场景的增强，并补章叠加；暂不更换模型。** 以下为待实施方案，本次没有修改 dataset.py。

1. **先区分增强适用场景。** 用来源/scene manifest 标记“识别正文、印章是干扰”的文档；正常红字、红底白字、需要识别章内容的图单独处理。不能靠“有红色”自动判断语义。
2. **先单测文档关闭 Invert。** UI 保持现有策略；ColorJitter 先保留，避免同时改多个变量。随后需要时再分别关闭 hue/saturation、Autocontrast，判断颜色扰动净收益。
3. **加入真实对应的章叠加。** 放在 `load_rgb_image` 之后、`resize_detection_image` 之前，让正文和章一起缩小。模拟圆弧、章文字、星形、局部出框、墨色和透明度，GT 保持正文。
4. **给出可执行起点。** 对适用文档用条件概率 0.15，alpha 先取 0.15～0.45，局部覆盖；记录 mask/seed，剔除完全不可读的叠加。这些是实验起点，不是已验证最优参数。普通 alpha 会染浅黑笔画，应同时检查保留深色笔画的乘性墨迹近似。
5. **随机擦除独立处理。** 先做文档 `p=0` 对照；若保留，应限定合理像素范围并检查笔画可读性。单纯提高擦除概率不会教会模型忽略章。

最小对照顺序：

| 实验 | 相对变化 | 要回答的问题 |
| --- | --- | --- |
| A | 当前五份训练数据、当前 RGB/32 高/增强 | 建立可重现基线 |
| B | A 仅关闭文档 Invert | 反色是否损害目标场景 |
| C | B 加上述受控章叠加，其余增强保持一致 | 补上章任务是否有效 |
| D | B 仅关闭文档 RandomErasing | 随机块是否损害细笔画学习 |

全部固定字典、初始化/初始权重、采样规则和更新步数；验证按相同步间隔进行。分别报告红章、普通文档、合法红字、白字 UI、小字的 CER/全串准确率，以及逐图改善、变差、删除和插入。
红章改善同时要求控制场景不退化；小数点、数字和末字单列检查。43 张清单里 29 张是 train、14 张是 val，只适合调试，不能作为独立业务准确率。

## 4. 训练链路的其他关键问题

| 问题 | 代码依据 / 实测 | 后续动作 |
| --- | --- | --- |
| **红章训练图是否也学不好** | 历史错误中已有 29 张 train 图；不能只解释成没见过验证场景 | 分别测无增强 train 红章与独立文档红章。前者差先查 GT/可读性/容量；前者好后者差再补来源覆盖 |
| **固定 batch 成员** | sampler 每轮按宽高比排序、切成 64，再只打乱 batch 顺序 | 单测较宽长度桶内重组，例如每桶 20 个 batch；记录来源和 padding 比例，避免直接混合极端宽度 |
| **训练 BN 仍受 padding 影响** | pack 在 CNN 后；BatchNorm 对 N/H/W 统计。相同内容只增加背景，随机 CNN 的有效特征差：eval=0，train=5.356 | 当前批次测试验证推理稳定，不能推出训练无 padding 影响。先监控实际占比，再决定是否单测固定 BN 统计；不要回滚 PackedSequence |
| **CTC 步数不是这批红章首要问题** | 当前 `T=(w+1)//4`；43 张红章均满足“标签长度+相邻重复对数”，余量 83～247 | 重点检查视觉分离；不要把 CNN 保护区计入 img_widths 来强加 blank 步 |
| **模型选择只看总体 CER** | CTC mean 按标签长度归一化后按样本平均；scheduler/Top-K 实际按 val CER，不是注释的 Loss | 加场景指标，防止普通文字收益掩盖红章退化；不直接换骨干或增加 680 轮 |
| **异常更新与恢复训练** | finite 检查在 optimizer.step 后；norm 在裁剪后记录；每次新建模型，仅保存 state_dict | 更新前检查 loss/梯度，记录裁剪前 norm，保存 optimizer/scheduler/seed/数据和 keys hash |
| **独立评估不可复现** | `VAL_ANNOTATION` 均被注释；GT 用 basename stem 关联，输出固定文件 | 改显式参数和独立输出目录，以完整样本路径关联，记录版本与场景 |

BN 的 train/eval 差异是机制演示，不是业务模型回退量。[BatchNorm2d](https://docs.pytorch.org/docs/2.9/generated/torch.nn.BatchNorm2d.html)
CTC 的 `zero_infinity=True` 只是把无穷 loss 及梯度置零，不能代替对齐校验。[CTCLoss](https://docs.pytorch.org/docs/2.9/generated/torch.nn.CTCLoss.html)

**高度 48 应放在增强对照之后。** 当前模型断言高度 32；改 48 后 CNN 输出高度为 2，需要仅沿高度汇聚，并同步训练/评估/导出/推理配置。等比宽度也约增 1.5 倍，要审计 1800 上限，避免额外横向压缩。
小字清单源高只有 18～25，放大不能恢复源图已丢的笔画；有高分辨率来源时先改善检测前的渲染。更强 CNN 只在监督和输入问题排查后单测，保留 GRU/CTC 作对照。

## 6. 追加：第一版 dataset.py 与当前版本的深度对比

### 6.1 对比版本与结论边界

这里的“第一版”明确指 Git 最早记录 **`b25d17a`（2026-06-15）**；当前文件对应 **`81153ca`（2026-09-05）**，本次工作区中该文件没有额外修改。
前文第 1～2 节的旧版是 **7 月 `b02fd0e`**。两者有关键区别：第一版去红**没有内容保护规则、膨胀两次，也没有白字自动裁剪**。不能把第 2 节“38 张改变、5 张保留”直接套到第一版。

**两版的核心差异是任务分工：第一版用较强规则预先消除红色，再学习以灰度文档为主的识别；当前保留颜色和正文细节，改善加载与序列边界，但需要模型承担正文/印章分离。当前工程正确性更好，不等于红章精度已经更好。**

### 6.2 同一图片经过两版时，模型究竟看到了什么

```text
第一版：直接 RGB 读取 → 无保护去红 → 按 nc 决定是否转灰度
        → 含高图特殊规则的 resize → 窄图补白 → 训练时几何/颜色/退化增强
        → Normalize → 统一白色 batch padding

当前版：RGB 读取、EXIF 纠正、透明底合成 → 完整框 resize/窄图按背景补边
        → 训练时颜色/极性增强 → 按 nc 决定是否转灰度 → 退化/Normalize
        → 右侧固定保护区 + 按边缘颜色做 batch padding
```

通道数由调用方传入：两版 dataset 都可以走 1/3 通道，当时 `train.py` 配置为 **1**，当前为 **3**。不能把 RGB 切换全部归到 dataset 的内部默认值。
第一版去红放在公共加载函数中，**`is_train=False` 仍会去红**；因此替换 dataset 后，旧权重的验证/推理输入也会立即变化。训练增强只在重新训练时起作用，这两类影响必须分开。

灰度转换顺序也变了：第一版在 resize 和 ColorJitter 前转 L；当前即使 `nc=1`，也是先处理 RGB 颜色，再转灰度。让旧灰度权重自动匹配到 1 通道，仍不能恢复它的旧输入分布。
Normalize 从 `[0.5]` 改为按通道重复的 `[0.5,0.5,0.5]`，对相同 RGB 张量的数值计算相同，本次已检查；这不是红章颜色变化的来源。

### 6.3 确定性加载和监督文本：哪些是修复，哪些是新边界

| 环节 | 第一版 | 当前版 | 训练含义 |
| --- | --- | --- | --- |
| 透明图片/方向 | 直接 `Image.open(...).convert('RGB')`，不处理 EXIF | 纠正方向，透明图根据可见亮度选黑/白底合成 | 避免直接丢 alpha、暴露隐藏 RGB；合成仍是底色估计，不能保证所有复杂透明图都最优 |
| 完整框 | 没有白字二次裁剪 | 没有二次裁剪 | **这一点第一版和当前相同**；自动裁剪是中间版本引入后又移除的 |
| 单字窄图 | resize 后不足 48，居中补白 | 不足 48，按四边颜色中位数居中补边 | 最小宽度 48 是沿用；改进的是背景适配，不是新增 CTC 时间步保障 |
| 标注解析 | 单份文件，按逗号拆分后重组文字，删除文字里所有 ASCII 双引号 | 多份文件，共享 Tab 解析，保留正文双引号 | 监督内容确实改变了；第一版会删除本应识别的引号，标点指标不能直接跨版本比较 |
| 空标签/坏行 | 空标签可进入 dataset；格式不符的行可能直接略过 | 空标签计数跳过；坏行汇总报错 | 当前更容易暴露标注问题，但仍不是逐图语义校验 |
| 缺图/解码失败 | 取样异常后返回全白 `[C,32,8]`，仍配原标签 | 先查精确路径；取样失败抛出含路径异常 | 修复了“白图配真实文本”的静默监督污染，不应回退 |
| 损坏数据边界 | `LOAD_TRUNCATED_IMAGES=True`；扫描异常用比例 1.0 | 仍保留这两项 | 部分截断图可能继续加载；完整健康审计不是本轮已经实现的能力 |

缺图问题会进一步影响 CTC：第一版的 dummy 宽度 8 只有约 2 个时间步。若原标签有 10 个字，配合当时的 `zero_infinity=True`，不可对齐样本的 loss/梯度可被置零；若标签足够短，则可能从空白图学习输出文字。两种情况都不能看作训练正常。
当前启动时发现缺图并报错，属于阻止错误训练，不是数据利用率下降。

### 6.4 红章：第一版清除得更多，也抹掉更多深色信息

本次重新在内存中提取第一版函数，对同一批 43 张图运行；SciPy 为 1.15.3，原图 hash 与已有清单一致。这里只比较**去红步骤**，不包含灰度、resize 或随机增强。

| 去红版本 | 规则 | 改写图片数 | 改写像素总数 | 抹白的低色差深色像素 |
| --- | --- | ---: | ---: | ---: |
| 第一版 `b25d17a` | 无内容保护；膨胀 2 次、闭运算 1 次 | 43 / 43 | 320,098 | 6,119 |
| 中间版 `b02fd0e` | 内容留存阈值/红色面积保护；膨胀 1 次 | 38 / 43 | 234,552 | 2,227 |
| 当前版 | 不执行去红 | 0 / 43 | 0 | 0 |

深色像素定义与第 2 节一致，不能把 6,119 解释成丢失字符数。当前列的 0 仅表示没有“去红抹白”，不表示缩小图像没有信息损失，也不表示识别更准。
`000570-000010.png` 在第一版会改写 **10,445 像素**，其中深色像素 **112 个**；中间版则被保护规则完整保留。因此“旧版是否处理这张图”必须先说明旧版是哪一次提交。

对黑字与红色可分离的扫描件，第一版可能有效降低背景干扰；对章与笔画混合、红色正文、红底白字，规则也可能直接销毁需要保留的信息。第一版没有训练模型识别“红色是否属于正文”，而是在模型前替它作出了固定判断。
**整版恢复第一版会同时恢复去章收益与误删风险；当前更合理的验证对象是颜色处理这一项，而不是把全部数据加载改动一起回滚。**

### 6.5 缩放不是简单地从“拉伸”改成“等比”

第一版先计算 `u=int(W*32/H)`；若 `u<int(W*0.5)`，便直接设为 `min(int(W*0.5),800)`。这不是一般的宽度下限，800 上限有时反而把已经算出的宽度压小。
第一版接收的 `img_width=1800` **实际上不生效**。当前按 `round(W*32/H)` 缩放、至少 1 px，并真正应用可选的 `max_width`；窄图补边发生在这之后。

| 原图 W×H | 第一版输出宽度 | 当前输出宽度，max_width=1800 | 影响 |
| --- | ---: | ---: | --- |
| 1200×96 | 600 | 400 | 第一版人为横向放大、给出更多时间步；当前保形，但对这类高框可减少有效序列长度 |
| 1989×69 | 800 | 922 | 第一版“保护”反而压窄；当前这张真实红章图更宽，不能说新缩放统一不利 |
| 2000×32 | 2000 | 1800 | 第一版忽略宽度参数；当前横向压缩，超长行需要额外检查 |
| 10×32 | 48 | 48 | 两版都靠画布补边，字符本身都不被拉到 48 宽 |

第一行和第三行是尺寸探针，第二行对应真实 `000249-000009.png`。这些数字来自实际代码路径/公式核对，不是训练收益。
普通图的 `int`→`round` 还可能改变 1 px；它会影响卷积时间步取整，不能在精度对照时把新旧预处理张量当成完全相同。
当前训练/训练期验证有 1800 上限，而独立评估和部署默认没有；共享同一个函数还不等于调用参数完全一致。

### 6.6 增强的实质变化：从几何与像素破坏，转向颜色和极性变化

具体概率与强度见第 1 节；第一版需要额外强调四点：

1. **“轻微旋转”对长行可能并不轻。** 第一版在 resize 到 32 高之后旋转，`expand=False`。1000 px 长行的两端距中心约 500 px，旋转 2° 的纵向位移约 17.4 px，已经超过画布半高 16 px，紧框末端可能被切掉。删除它减少了真实字符被裁切的风险，也减少了倾斜样本覆盖。
2. **第一版透视并未指定 fill。** 在当前 TorchVision 0.24 重放时默认为 0，旋转却明确用 255；同一条白底文字可能获得不同填充颜色。7 月版后来指定了透视白底，因此不能沿用它的解释来描述第一版。
3. **颜色增强改变了实际学习目标。** 第一版默认先去红、转灰度，saturation 参数对 L 图不提供颜色变化；当前在 RGB 上作用，contrast 范围变为 0.75～1.25、saturation 为 0.65～1.35，且新增 hue 与反色。模型需要利用颜色区分干扰，同时学习对这些颜色变化保持稳定；有益还是有害需要分场景检验。
4. **像素退化明显减轻。** 只看模糊、噪声、擦除三个概率开关，“至少一个被选中”的理论概率从 `1-0.7*0.7*0.82=59.82%` 降为 `1-0.85*0.85*0.95=31.36%`。这不是实际破坏比例，擦除还可能因形状采样失败而不生效，但足以说明当前没有全面加强退化。

两版都是先 resize 再做这些训练增强，所以“先缩到 32，再模糊损伤细笔画”属于共同问题。当前噪声改用 `randn_like` 并限制范围，擦除却仍可能越界；不能将噪声修复和擦除遗留问题混为一谈。
更关键的是，第一版靠规则去章，当前没有去章也没有章叠加训练；**增强整体变轻并不保证模型接住了新增加的正文/印章分离任务**。

### 6.7 batch 与序列边界：哪些真的改了，哪些从第一版就存在

`BucketBatchSampler` 两版的 AST 完全一致：预扫描原图宽高比、排序、按 batch_size 切块、只打乱 batch 顺序。固定成员、没有难例配额、没有来源权重都属于遗留行为。增加多份标注改变了候选样本及成员组合，但没有改变采样算法。
DataLoader 的训练 `drop_last=False`、验证 `shuffle=False`、自定义 collate、pin_memory 等关键配置也沿用原逻辑。

| collate 行为 | 第一版 | 当前版 |
| --- | --- | --- |
| batch 最大宽度 | `ceil8(max(w))` | `ceil8(max(w)+32)` |
| 补齐颜色 | 所有图固定为 Normalize 后的白色 1.0 | 每张图取右侧最多 4 列的各通道中位数 |
| 64 px 图单独组 batch | 张量宽度 64，右侧无保护区 | 张量宽度 96 |
| 同 256 px 图一起组 batch | 张量宽度 256 | 张量宽度 288 |
| 返回的 img_widths | `[64,256]` | 仍是 `[64,256]`，不含新保护区 |

第一版同一张图单独推理时 CNN 可能直接接触张量边界，混入长图时却看到白色补齐；当前保护区改善这个问题。代价是每个 batch 张量额外增加固定背景宽度，短图的相对开销更明显。
当前补色更适合深色/彩色背景；若右边几列主要被章或实线占据，也可能估到前景色。该风险需针对贴边样本检查。本次 43 张确定性输入的补色探针中，没有出现 `R>G+30 且 R>B+30` 的明显偏红补色，不能将此风险认定为本批红章错误原因。

**保护区不等于 PackedSequence。** 前者在 dataset 修复 CNN 局部边界，后者在 model.py 修复反向 GRU 读取 padding；两项缺一不可。第一版也返回 img_widths，只是旧 GRU 仅把 padding 特征置零，训练后的 bias 仍可改变隐状态。
两版 CNN 的训练 BatchNorm 都统计补齐区域，当前并未实现“训练完全不受 batch 背景影响”。这些区别决定了为什么不能为改善红章而恢复第一版 collate 或忽略 img_widths。

### 6.8 能归因于 dataset 的变化，与必须分开验证的变化

| 判断 | 依据 |
| --- | --- |
| 应保留的明确修复 | 精确路径和错误异常、透明图合成、正文引号保留、适配背景的补边、固定 CNN 保护区；这些解决可直接从代码复现的问题 |
| 红章优先验证项 | 去红撤除后模型是否能拟合正文；文档反色/颜色扰动是否过强；有无真实对应的章覆盖训练 |
| 不能归因于本次新增的缺点 | 固定 bucket 成员、32 高后做模糊、随机擦除越界、允许部分截断图；第一版已经存在 |
| 不能只用 dataset 解释的指标差异 | 第一版 train.py 为 1 通道、单份数据且用 train 同时验证；当前为 RGB、多来源及独立 val，还改过字典和 GRU 路径 |

另有一项调用方差异：第一版 train.py 用 `w//4` 作为 CTC 输入长度，model.py 已按实际 CNN 使用 `(w+1)//4`；当 `w%4==3` 时会相差一步，例如宽 59 时是 14 对 15。当前统一使用模型长度公式。这个末端监督差异不能算作 dataset 的红章增强问题。

如果要回答“第一版为什么更准”，必须先绑定同一权重、字典、验证图片和标签规范；只替换预处理得到的是输入敏感性，不是新旧训练的因果对照。仅开关去红的训练对照还应保留相同通道、增强、长度公式与更新预算。
本节只追加文档，未调整代码、数据或既有诊断脚本；新增第一版像素数来自本次只读内存探针，第 5 节脚本仍以 7 月版本为去红对照。
