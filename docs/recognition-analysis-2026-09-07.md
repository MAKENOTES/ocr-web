分析日期：2026-09-07。代码基线：`119c7b8`。
指定权重：`recognition/checkpoints/1788725792best_cer_0.0082_epoch_471.pth`。

## 1. 结论与证据范围

当前最值得优先解决的是标注残留、长尾字符及红章/低分辨率场景的训练覆盖。
CNN 容量很小，值得做更强视觉骨干的对照，但现有证据不支持把主要错误归因于
9 月 3 日的 PackedSequence 修改，也不支持直接回滚该修改。

本次完成了五份标注的全量字符统计、136,874 张图片的尺寸/模式头信息扫描、
训练日志读取，以及人工清单中 104 张不重复图片的 CPU 推理复测。
图片推理复用当前 RGB 加载、等比缩放、动态 padding 和 greedy decode。
另外进行同一权重的旧 GRU 路径、混合宽度 batch 和输入张量探针测试。
原图、标注、字典、权重及训练/推理主链路均未修改，也未启动重新训练。

104 张是人工挑选的历史错误，不是随机测试集。下面的“43 张红章”“8 张小字”
只能描述这些样本，不能当作整个红章/小字群体的准确率。清单中有 16 张在指定权重下
已经正确，因此原有分类和历史错误需要与具体 checkpoint 绑定。
总体 val 指标来自现有 TensorBoard 日志，不是本次重新跑全量 val 的结果。

### 2.2 append 中存在明显的转义残留

`append_annotation.txt` 有 7,012 条样本包含 `\"`，共有 9,415 个反斜杠，
所有反斜杠都紧贴双引号。它们占 append 样本的 20.58%、全部训练样本的约 5.51%。
当前解析器不会反转义，因此这些反斜杠都作为训练目标进入 CTC。

抽查 `du20260904-append-img_0000001.png`、`du20260904-append-img_0000014.png`，
图片里只有引号，没有标签中的反斜杠。这是直接可见的标注问题；7,012 条尚未逐图人工核对。
当前 `recognition/error_cases.txt` 还出现了引号前额外输出反斜杠的案例，与该污染方向一致，
但该文件没有 checkpoint/数据集元信息，不能据此精确量化指定权重的受影响程度。

建议回溯 append 的来源格式，在数据导入处明确执行一次合法的字符串反转义，
生成新版本标注并保留差异清单；不要全局删除所有反斜杠，真实路径、公式等可能需要它。
这次没有改写任何标注。

### 2.3 标点规范还没有完全统一

英文 `,` 的次数在 train/val/append/bench1/bench2 中分别为
109/26/0/4,124/2,368；中文 `，` 对应 5,483/1,326/26,614/11,975/6,300。
英文 `;` 对应 565/142/0/964/618，中文 `；` 对应 124/33/227/0/0。
这证明不同数据源的分布差异很大；是否每一处都属于错误，还需对图核实。

中文语句里的逗号/分号应明确输出规范；小数点、版本号、路径、URL、英文技术短语要保留
有意义的标点差异。训练标签、评估和产品输出必须使用同一份版本化规范。
可同时报告原始 CER 与业务归一化 CER，避免用过度归一化掩盖金额等内容的错误。

## 3. 红章：主要是视觉遮挡和场景覆盖不足

清单中 43 张红章图：train 29 张、val 14 张。原图高度为 38～69 px，
统一缩到 32 px 后，原本混杂的黑字与红色笔画进一步混合。
这些样本不属于“源图片本身只有十几个像素高”的小字情况。

例如 `000570-000010.png`：标签片段“审计范围、时间安排和重大审计发现”，
当前输出“审计福围时间安排和重天审计发现”。打开原图可以看到，错误附近存在
红色文字、圆弧或五角星，与黑色正文重叠。
`000874-000025.png` 的“丢失，乙方”附近也被红色圆弧/文字干扰。

### 3.1 同一权重的颜色探针

保持全部文件不变，只在内存中将已经预处理的 RGB 张量替换为 R 通道复制三份，
或替换为灰度复制三份；使用相同模型、同样的有效宽度和解码。
R 通道里红色印章与白底较接近，而黑色文字通常仍较暗，所以这个探针有助于检验颜色干扰。

| 43 张人工红章样本 | 全串正确数 | 编辑错误总数 | 相对 RGB 改善/变差的图片数 |
| --- | ---: | ---: | ---: |
| 当前 RGB | 0 | 110 | — |
| R 通道复制三份 | 10 | 84 | 24 / 8 |
| 灰度复制三份 | 2 | 126 | 5 / 13 |

这支持“颜色/印章干扰确实是当前模型的一项弱点”。但 R 通道仍使 8 张变差，
剩余错误中也有标注歧义，不能把结果理解为已经找到可直接部署的去章方案。
探针未评估正常红字和彩色 UI 文本；统一去红会损失这些合法内容。

### 3.2 训练链路缺少对应的增强

当前增强是 ColorJitter、Autocontrast、Invert、轻模糊、噪声和小面积 RandomErasing。
其中没有印章圆弧、章中文字、五星、透明度变化或局部重叠的模拟。
RandomErasing 也不等价于红色透明图形与正文叠加。
bench1/bench2 共 55,035 张，占四份训练集的 43.22%，磁盘模式全部是灰度 `L`；
转为 RGB 后不会自动产生红章场景的颜色信息。当前自然混合没有难例配额。

建议优先实施：

1. 核验真实红章样本的 GT；对无法从原图确定的字明确记录可读性，避免把猜测文本当可靠监督。
2. 在可读的正文上合成不同透明度、色深、印刷模糊、角度、覆盖位置的红章。
   将全遮挡与可辨认遮挡分级；过强遮挡配完整文本容易迫使模型依赖语言猜测。
3. 保留正常黑字、红字、白字 UI 的训练比例，再给已核验红章难例设置采样配额。
   可从每批约 10%～20% 的受控难例比例试验，观察普通样本是否回退；这是待验证的起点。
4. 比较 32 与 48 高度、较强 CNN 的收益。优先让模型利用 RGB，通道增强/辅助分支可以
   作为训练消融，最终要在红字和 UI 控制集一起验收。

### 4.1 没有出现硬性的 CTC 长度不足

这 8 张图有效时间步为 115/17/15/14/34/18/31/19，目标最少所需步数分别为
18/2/3/3/6/3/6/3。最少步数按“标签长度 + 相邻重复字符对数”计算。
五份数据的 136,874 张图都通过这个必要的对齐可行性检查。
训练最大宽度上限为 1,800，实际等比宽度最大值为 1,733，当前没有上限造成的横向压缩。

但“步数够”不等于末字特征/对齐一定好。只在小字图的有效画布右侧增加 8 px 背景，
再额外使用原有 CNN 保护区，`贾含笑` 就恢复了；8 张的编辑错误总数从 8 降为 7。
这提示边缘上下文/CTC 对齐值得单独检查，但还不足以推广为统一修改。
不能简单把 `CNN_RIGHT_CONTEXT` 加进所有 `img_widths`，那会改变已有长度语义。

水平放大 1.5 倍的诊断也仅让 3 张改善、2 张变差，总编辑错误仍是 8。
因此直接拉宽输入没有获得一致收益。完整预测见 [probes.json](../outputs/recognition_audit_20260907/probes.json)。

### 4.2 小字改进顺序

先把“源分辨率低”“字形占框比低”“表格线邻接”“稀有字”“末字漏识别”分别标记。
补充同来源的小字号姓名/机构名数据，增加细字体、不同抗锯齿和缩小再放大的退化样本。
对原本已很小的样本降低模糊/擦除强度，避免删掉决定形近字的唯一笔画；保持适量退化以
覆盖真实模糊，具体强度通过消融选择。

48 高度值得尝试，但当前模型断言高度必须为 32；输入 48 经 CNN 后高度是 2，
不是 1。需要修改高度压缩方式，例如仅沿高度汇聚到 1，重新训练，并同步更新
数据加载、导出与多后端测试。宽度也随高度变为约 1.5 倍，1,800 的上限和计算开销要重算。
它能减少预处理中丢失细节，但不能凭插值创造原图没有的信息。

## 5. 最近 model.py 修改的实际影响

`git log -- recognition/models/model.py` 只有 `b25d17a` 和 `a228b2b`。
`b25d17a` 的该文件已经是 Mobile CNN + BiGRU。
最近提交 `a228b2b`（2026-09-03，批次优化）改变的是：

- 原先先把 padding 特征置零，再让 GRU 跑完整个 batch 最大长度。
- 现在按真实长度 pack/unpack，使正反向 GRU 真正跳过 padding。
- 时间步计算向量化，输出 padding 显式置为 blank。

这次没有修改 CNN 层数/通道、输入高度、GRU hidden、GRU 层数和分类头。
同一提交还调整了 collate 右侧保护区和显式 TBC/BTC 解码，都是不同的控制点。
训练后的 GRU 存在 bias，零输入区域的隐状态不保证保持为零，因此旧方法不等价于跳过 padding。

### 5.1 同权重、同预处理的受控比较

本次将指定权重分别放入当前 forward 和按旧逻辑重建的 forward。
两者都使用当前 CNN 保护区，只隔离 GRU 的差别。每张图比较 batch=1 与加入固定长图的
batch=2（控制图宽度取至少 1,024，且不小于清单最长图）。

| 104 张人工清单 | 当前 PackedSequence | 旧的零 padding GRU |
| --- | ---: | ---: |
| batch=1 全串正确数 | 16 | 18 |
| 换长图 batch 后文本变化数 | 0 | 15 |
| 红章 43 张全串正确数 | 0 | 0 |
| 小字 8 张全串正确数 | 1 | 3 |

当前有效 log-probability 最大 batch 差异约 `8.96e-5`，文本完全一致。
旧方法有少数单图结果更好，这是实测结果；但它同时使预测依赖同批其他图片的宽度。
这不是稳定的精度收益，也不解决红章组的主要错误。

这只是“新权重套旧运行逻辑”的诊断，不是同训练预算的新旧训练 A/B；也没有执行整个
旧提交的预处理。权重只含 state_dict，没有保存训练 git hash，所以无法仅凭权重文件
证明当时实际执行的每一项源码。要量化修改对训练的因果影响，需要相同数据快照、seed、
更新步数、增强及评估规则分别训练两种实现。

现有 batch 一致性测试全部通过，包括 PyTorch、ONNX 和 OpenVINO 的测试模型。
这些测试没有重新导出本次指定的完整 4,694 类权重，不能替代发布前该权重的多后端验收。

| `CTCLoss` | 真实长度和模型一致，`zero_infinity=True` | 保留对齐长度检查；不让 zero_infinity 静默吞掉未来不可对齐样本 |
| `train.py:227–238` | finite 检查在 backward/step 之后，仅用于日志 | P2 在 backward 前检查 loss，更新前检查梯度；本次没有 NaN 故障证据 |
| `log_gradient_norms` | 记录的是裁剪后的梯度 | P2 同时记录裁剪前 norm，便于判断不稳定性 |
| 训练验证与 Scheduler | 实际按 val CER 调度和保存，部分注释仍写 Loss | P1 记录宏平均字准确率和场景指标，校正文档/注释 |
| `torch.save(state_dict)` | 无 optimizer、scheduler、seed、数据/keys hash、代码版本 | P1 保存可恢复训练状态和 run manifest，精确记录未四舍五入指标 |
| `evaluate_val.py` | 所有 `VAL_ANNOTATION` 定义当前均被注释；没有 CLI | P1 改成显式参数、独立输出目录；当前直接运行会 NameError |
| 独立评估图片身份 | 通过 basename stem 查 GT，同名图片会覆盖 | P1 按完整路径/样本 ID 绑定；本次清单均唯一匹配 |
| 独立评估输出 | 固定 error_cases.txt，会被下一次评估覆盖 | P1 文件中保存模型、manifest、预处理和数据版本 |

CTC 的 `zero_infinity` 会将无限 loss 及其梯度置零，并不会自动修复数据；
`reduction='mean'` 先按目标长度归一化，再求 batch 平均，目标函数也不等同于总体 CER。
参见 [PyTorch CTCLoss 官方说明](https://docs.pytorch.org/docs/stable/generated/torch.nn.CTCLoss.html)。

还有两项数据质量边界：`LOAD_TRUNCATED_IMAGES=True` 允许部分截断图继续读；
桶采样扫描异常会先回退比例 1.0，正式取样才报错。可以增加训练前完整解码审计。
本次尺寸检查读取的是图片头，只有 104 张清单图及少量抽查图做了完整加载，
不将“尺寸扫描通过”等同于全部图片内容健康。

### 6.1 验证集独立性

train/val 图片 basename 交集为 0。按文件名最后一个 `-` 前的前缀粗略分组，
train 有 9,222 个前缀，val 有 3,017 个，交集 1,362 个。
这些前缀不一定都是文档 ID，不能把 1,362 直接当作泄漏文档数；但它说明当前划分
不能证明文档/来源独立。应根据真实 PDF、网站、模板、截图会话和合成模板做 group split。
本次未对全部图片执行内容 hash/感知 hash 去重，不能据 basename 无交集宣称完全无泄漏。

本项目是 BiGRU + CTC greedy 解码，重复/插入不等同于大语言模型式的自由生成。
同字符被 blank 隔开时会保留两次，文本真实重复也必须保留；后处理去重会误伤
数字、姓名、编号等。Beam search 可以另做解码对照，但对视觉遮挡、稀有姓名和错误 GT
没有必然修复作用，也不宜先加通用语言纠错把低频真字改成常见字。

## 7. 是否替换 model.py：建议先测 ResNet18，再比较轻量方案

指定权重实际参数量：CNN **137,792**，BiGRU **789,504**，分类头 **2,408,022**，
合计 **3,335,318**。视觉骨干只有约 0.138M 参数，而分类头占约 72.2%。
文件开头对 CNN“约 0.5M”和速度“3～5 倍”的描述不是本次架构/硬件的实测结果。
当前 CNN 没有残差连接，也不是 TorchVision 的 MobileNetV3。

这些事实说明视觉容量值得检查，但参数少本身不是因果证明。
优先增强 CNN 的对照价值高于立即增加 GRU 层数；姓名稀有字和红章笔画需要更好的视觉信息，
单纯加强上下文也可能增加常见字替代稀有字的倾向。

用户提供的 [TorchVision 模型目录](https://docs.pytorch.org/vision/stable/models.html)
列出的是分类等通用任务模型，并没有可直接替换本项目 CRNN 的完整中文识别器。
下面的参数量是官方原始分类模型的总参数，包含 ImageNet 分类头，
**不是改造后 OCR 模型的参数量或 OCR 精度**。

| 候选 | 官方分类模型参数 | 对本项目的判断 |
| --- | ---: | --- |
| [ResNet18](https://docs.pytorch.org/vision/stable/models/generated/torchvision.models.resnet18.html) | 11.69M | 第一组精度对照；残差骨干，适配相对清楚，但 CPU 成本需实测 |
| [MobileNetV3-Large](https://docs.pytorch.org/vision/stable/models/generated/torchvision.models.mobilenet_v3_large.html) | 5.48M | CPU 成本敏感时优先比较；有倒残差/通道增强，但 SE 必须处理 padding |
| [EfficientNet-B0](https://docs.pytorch.org/vision/stable/models/generated/torchvision.models.efficientnet_b0.html) | 5.29M | 备选；同样有 SE 和宽度步长适配成本，不能凭 ImageNet 指标排在前面 |
| [ConvNeXt-Tiny](https://docs.pytorch.org/vision/stable/models/generated/torchvision.models.convnext_tiny.html) | 28.59M | 更大的对照；入口降采样和资源成本更高，不是当前第一轮实验 |

### 7.1 ResNet18 推荐适配方式

保留 RGB、可变宽度、单层 BiGRU 和 CTC；去掉分类器与跨宽度的全局池化。
将 layer2/3/4 首块和 shortcut 中的宽 stride 改为 1，使总宽降采样约为 4；
必要时用 1×1 卷积把 512 通道投影到 256，以便保持相同 GRU 做受控比较。
高度 32/48 分开试，48 的末端只沿高度汇聚。

ResNet 的 maxpool 带 padding，真实长度公式与当前 Mobile CNN 不同，不能原样复制
`_calc_cnn_output_widths`。感受野扩大后，现有 32 px 右侧保护区也不能照搬。
这两项要用单图/混合长度 batch、长图、边缘字和 ONNX/OpenVINO 一起验证。

使用 ImageNet 预训练可以作为初始化实验，但不能套用官方分类用的 224×224 center crop，
那会截掉文字行。预训练默认均值方差也不同于当前 `[0.5]/[0.5]`；应选择并版本化 OCR
训练/推理的统一归一化规则，不在部署时突然切换。官方对预训练预处理的要求见
[MobileNetV3 权重说明](https://docs.pytorch.org/vision/stable/models/generated/torchvision.models.mobilenet_v3_large.html)。

历史文件 `model_resnet50.py` 实际使用 ResNet34 + 两层 BiLSTM，名字不准确。
它只在 RNN 之后 mask、未用 PackedSequence，且缺少当前统一长度接口。
可以参考其非对称 stride 思路，但不能直接把 import 切过去当成合格替换。

### 7.2 MobileNetV3 的一个关键适配陷阱

MobileNetV3 使用 Squeeze-and-Excitation，官方 SE 内部含 `AdaptiveAvgPool2d(1)`，
在整个空间上求均值。依据 [MobileNetV3 源码](https://docs.pytorch.org/vision/stable/_modules/torchvision/models/mobilenetv3.html)
和 [SE 源码](https://docs.pytorch.org/vision/stable/_modules/torchvision/ops/misc.html)，
可以推断：若直接把带额外右侧 padding 的图送入未改造 SE，通道权重会随 padding 比例变化。
仅修复 GRU 或增大固定右边界不能消除这种全局依赖。

需要在各阶段跟踪有效宽度，使用排除 padding 的空间均值，或选择没有这种全局空间操作的
骨干。此点也是先用 ResNet18 做精度对照的工程理由。真正部署时仍要测实际 CPU
延迟、峰值内存及 batch=1/64，不能根据官方分类 FLOPs 直接推断长文字 OCR 耗时。

如允许引入 OCR 专用方案，还可以将 PP-OCR/SVTR 系列作为外部基准或教师模型；
它们提供识别任务专用网络与预训练，见 [PaddleOCR 官方识别模型说明](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/OCR.en.md)。
这需要独立接入、字典/输出规范评估，不能直接加载当前 pth，也不能把其官网指标与本项目 CER 横比。

## 8. 推荐的实验顺序与验收

| 实验 | 相对于基线只改变什么 | 要回答的问题 |
| --- | --- | --- |
| A0 | 固定当前 32 高、当前 CNN、PackedSequence 与数据快照 | 可重复的基线是什么 |
| A1 | 核验后的标注与规范 | 去掉转义/GT 污染能改善多少 |
| A2 | 在 A1 上补充红章/稀有字/小字数据，并限制采样比例 | 场景覆盖是否是主要瓶颈 |
| B1 | A2 数据，CNN 改 ResNet18，仍高 32、同 GRU | 更强视觉骨干是否有效 |
| B2 | A2 数据，当前 CNN 适配高 48 | 提高输入细节保留是否有效 |
| B3 | A2 数据，ResNet18 高 48 | 两项组合是否值得成本 |
| C1 | 精度目标明确后再测 MobileNetV3 或蒸馏 | 如何降低部署成本 |

所有实验固定验证集、keys、标签规范、随机种子和可比较的训练更新预算；
采样规则改变后不能只比较相同 epoch 数。至少报告总体 CER/全串准确率、
红章、低源分辨率、罕见字、标点、长行、正常红字/白字 UI 的子集指标，
并分开统计替换、删除、插入、末字漏识别。小样本改善不直接作为发布结论。
按每个字符的召回率做宏平均，补足总体 CER 对高频字的偏重。

本次已有验证：新增统计脚本 8 项测试、共享预处理 9 项测试、batch/后端一致性 6 项测试，
共 23 项通过。其中后端导出有现有 legacy ONNX/Tracer 警告，测试本身通过。
尚未训练或评测候选骨干，替换收益、红章增强比例及高度选择仍需要上述对照实验证实。
